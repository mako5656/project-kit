## 技術構成

- 【要入力：言語・フレームワーク・DB とバージョン。例：Node.js 26 / Next.js 16（App Router・TypeScript）/ PostgreSQL 18.6】。アプリはリポジトリ直下に置く。
- 【要入力：ORM・マイグレーション・テスト・Lint・整形のツール】
- 依存管理は【要入力：npm・Bundler など】に統一する。別の言語で書く補助ツールは、置き場所と依存を分ける。
- ローカルの DB は`docker-compose.yml`で起動する（ポート【要入力】）。アプリは【要入力：起動コマンド】で起動する。
- 本番環境は【要入力：AWS・CDK など。未定なら「リリース直前に決める」】。それまではローカルで開発し、外部に依存する部分は差し替えられる形にする。

## 開発ルール

- `.editorconfig`に従い、UTF-8・LF・スペース2個・末尾改行を使用する。Markdownの改行用末尾スペースは保持する。
- 関数・メソッドの間とガード節の後は1行空ける。セミコロンで複数の処理を1行に詰めない。

- 【要入力：このプロジェクト固有の設計ルール。判断の理由は ADR に書き、ここには守るべきことだけを書く（例：「術式は設定データとして持つ（ADR-0004）」）】
- お金・契約・権限・個人情報に関わる変更には、意味のある回帰テストを追加する。DB の制約・トランザクション・冪等性キーで二重処理を防ぐ。
- `.env`・`.env.*`、認証情報、実データ、アップロード、依存ライブラリ、実行ログはコミットしない。
- 費用のかかる外部 API は、実行前に回数と概算の費用を示し、ユーザーが認めた範囲で呼ぶ。テストから外部 API・本番の DB・課金・メール送信を呼び出さない。
- 既存の DB やコンテナを停止・初期化しない。
- 仕様・構成を決めたら`docs/`の該当資料を更新し、判断の理由は ADR に記録する（[資料の置き方](docs/README.md#資料の置き方)）。
- 仕様・設計・参考資料は構成整理だけで削除しない。実行手順が変わった場合は資料と索引のリンクを更新する。
- 画面を変更したら、PC・スマホの表示をブラウザーで確認する。

## 検証

- 変更後は【要入力：`npm run check`・`bin/check` など、整形・Lint・型・テスト・ビルドをまとめて実行するコマンド】を実行する。
- 安全な自動整形は【要入力】。Lint のルールを一括で外して指摘を回避しない。
- DB に接続するテストは、テスト用の DB を分けて実行する。
- CI（GitHub Actions）は【要入力：導入済みなら対象と内容。未導入なら「完成が近づいたら入れる」】。プルリクエストを作る前に、ローカルでも同じ検証を通す。

## Issue

- 作業と未決定の論点は GitHub の Issue で管理する。ラベルは種類（実装・仕様・不具合・調査）・状態（要判断・作業中・着手可・レビュー待ち）・担当（Claude・Codex・ユーザー）・優先度（P1：公開に必須、P2：公開後すぐ、P3：余裕があるとき）を付ける。
- 本文は背景・決定（日付）・作業のチェックリスト・状態で書く。決定した内容は日付付きで Issue に残し、判断の理由は ADR に記録して Issue からリンクする。
- 着手したら`状態:作業中`、プルリクエストを作ったら`状態:レビュー待ち`にする。
- `担当:Codex`の Issue は、仕様・完成の条件・触る場所を本文に書き、Codex が質問せずに作業できる状態にしてから渡す。Codex の変更は Claude が確認する。

## ブランチとプルリクエスト

- `main`へ直接プッシュしない。作業は`main`から切ったブランチで行い、プルリクエストでマージする。
- コミットメッセージ・ブランチ名・プルリクエストのタイトルは[コミットメッセージ・ブランチ名の書き方](docs/開発ルール/コミットメッセージの書き方.md)に従う。
- 本文には変更の目的・内容・確認したこと・関連する Issue（`Closes #番号`）を書く。
